# Agent-to-Agent (A2A) Communication

This implementation uses a **custom, simplified** HTTP/JSON protocol,
self-labeled `"protocol": "http-json-a2a"` in each agent card. It takes
two ideas from the Google/Linux-Foundation Agent2Agent (A2A) specification
— agent cards for discovery, and structured task delegation — but is not
an implementation of that spec. If a reviewer is checking this against
the formal A2A spec, see [Differences from the formal A2A spec](#differences-from-the-formal-a2a-spec)
below before assuming any parity.

## Roles

- **`coordinator-agent`** — the only A2A *client* in this system. It is
  not itself discoverable (no agent card, no `/a2a/tasks` endpoint) and
  is not a worker for any other agent.
- **`customer-agent`** and **`order-agent`** — A2A *servers* ("workers").
  Each exposes an agent card and a single task endpoint. Neither one
  calls the other, or calls the coordinator back.

Discovery is one-directional: the coordinator discovers workers; nothing
discovers the coordinator.

## Agent cards

`GET /.well-known/agent.json` on each worker returns a static JSON
document (no dynamic content, no auth required to fetch it):

```json
{
  "name": "customer-agent",
  "description": "Provides customer information",
  "capabilities": [
    {"name": "get_customer", "description": "Retrieve customer information by customer ID"}
  ],
  "protocol": "http-json-a2a"
}
```

`order-agent`'s card lists two capabilities: `get_order` and
`get_latest_order` (see [docs/api.md](api.md)).

The coordinator fetches the relevant card **on every request** (no
caching), before delegating a task to that agent. In practice this
serves as a liveness check more than real capability negotiation: the
coordinator already knows which single capability it needs before it
asks (from its own keyword-based planner, see below), and the fetched
card's contents are only echoed back in the response under
`a2a.customer_agent`/`a2a.order_agent` — they don't change which action
gets requested.

## Task delegation

`POST /a2a/tasks` on a worker, body:

```json
{
  "task_id": "customer-<correlation_id>",
  "action": "get_customer",
  "customer_id": "C001"
}
```

- `task_id` is generated by the **caller** (the coordinator builds it as
  `f"{kind}-{correlation_id}"`, e.g. `customer-test-e2e-001`) — a worker
  does not mint its own task IDs.
- `action` selects behavior server-side (`get_customer` on
  `customer-agent`; `get_order` or `get_latest_order` on `order-agent`).
  An unrecognized action returns `400 UNSUPPORTED_ACTION`.
- The call is **synchronous**: the HTTP response body *is* the finished
  result (`"status": "completed"` always, when the call succeeds — there
  is no `"pending"`/`"running"` state ever returned). A failure is an
  HTTP error status with a structured `{"detail": {"error", "message"}}`
  body, not a `"status": "failed"` task object.
- No authentication header is sent by the coordinator to a worker, and
  no worker checks for one — A2A calls are unauthenticated. (Contrast
  with the worker → APISIX leg, which does require `apikey`.)
- `X-Correlation-ID` is forwarded by the coordinator on both the
  discovery and the task-delegation call, and the worker forwards the
  same value onward to APISIX — so a single ID threads through the whole
  chain, as long as the original client supplied one.

A worker executing a task makes exactly one downstream call to the
backend REST API, through the gateway:

- `customer-agent` → `GET {APISIX}/api/customers/{customer_id}`
- `order-agent` (`get_order`) → `GET {APISIX}/api/orders/{order_id}`
- `order-agent` (`get_latest_order`) → `GET {APISIX}/api/customers/{customer_id}/orders`,
  then picks `result[0]` (the service already sorts newest-first) — if
  the list is empty, the worker itself raises `404 LATEST_ORDER_NOT_FOUND`
  rather than returning an empty result.

## Orchestration (`coordinator-agent`)

`POST /agent/query` is the only entry point that triggers A2A activity.
Its planning step is intentionally simple and fully described in
[README → Agentic API](../README.md#agentic-api):

- A regex extracts a customer ID (`\bC\d{3}\b`) and, independently, an
  order ID (`\bO\d{4}\b`).
- **If no customer ID was found but an order ID was**, the coordinator
  discovers `order-agent` and delegates a single `get_order` task
  directly, by order ID — `customer-agent` is never contacted. This is
  the only path that exercises `order-agent`'s `get_order` capability
  (its other capability, `get_latest_order`, is used by the
  customer-centric path below).
- **Otherwise**, two independent substring checks on the lower-cased
  query (`"customer" in query`, `"order" in query`) decide whether to
  delegate to `customer-agent`, `order-agent` (via `get_latest_order`),
  or both.

There is no LLM, no tool-use loop, and no re-planning based on
intermediate results — the two delegations in the customer-centric path
(when both are needed) always happen in the same fixed order: customer
first, then order. A query containing both a customer ID and an order ID
takes the customer-centric path, and the order ID is ignored.

## Differences from the formal A2A spec

For anyone comparing this against the actual Agent2Agent specification:

| Formal A2A spec | This implementation |
|---|---|
| JSON-RPC 2.0 over HTTP (and/or gRPC) | Plain REST-style JSON POST, no JSON-RPC envelope |
| Task lifecycle with states (`submitted`, `working`, `input-required`, `completed`, `failed`, ...) and a `tasks/get` to poll | Synchronous only: one POST, one terminal result, no stored task state, no polling endpoint |
| Streaming updates via Server-Sent Events / push notifications | Not implemented |
| Rich "Agent Card" with auth schemes, skills, and structured input/output schemas | A minimal, hand-written static JSON document: name, description, a flat capability list, no declared auth scheme or schema |
| Authenticated agent-to-agent calls (per the card's declared auth scheme) | No authentication at all between agents |
| Multi-turn conversations / artifacts | Not implemented — each task is a single request/response with one `result` payload |

This system should be described as **"A2A-inspired"** or **"a custom
A2A-like protocol"**, not as a conformant A2A implementation.

## Failure semantics

Every outbound call a worker or the coordinator makes
(`httpx.AsyncClient(timeout=5.0)`) distinguishes three outcomes, and maps
each to a specific HTTP status and error code rather than letting an
exception propagate as a generic 500:

1. **Timeout** (`httpx.TimeoutException`) → `504`, `..._TIMEOUT`.
2. **Connection/transport error** (`httpx.RequestError`, e.g. the target
   container isn't running) → `502`, `..._UNAVAILABLE` (for discovery
   calls) or `..._ERROR` (for failed delegated work at a worker whose own
   downstream call failed).
3. **HTTP error status from the callee** (4xx/5xx) → passed through or
   remapped (404/429 preserved with a renamed error code; anything else
   → `502`).

See [docs/architecture.md](architecture.md#failure-path-behavior) for the
decision diagram and [docs/demo.md](demo.md) scenarios 4–7 for worked
examples with real commands.
